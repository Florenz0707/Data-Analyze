# development_plan 未完全达标指标改进计划

更新时间：2026-09-02
依据：`doc/development_plan.md` 第 4、5、6、7、8、9、17、18、19 章及 E-001～E-033 证据

## 1. 文档目的

本文集中整理已经有代码实现、测试或基准证据，但仍存在以下任一情况的指标：

1. 最新实测值低于 `development_plan.md` 规定的目标；
2. 实现已经完成，但测试范围不足以证明目标覆盖了真实部署条件；
3. 指标已经达到自动化代理门槛，但尚未完成计划要求的人工或非实现者复核；
4. 指标依赖仓库平台、生产部署或完整数据集，当前仍没有闭环证据。

M6～M9 中完全未开始的任务不列入本文；它们仍按总计划的里程碑顺序推进。本文也不重复列出已经有充分证据达标的指标。

## 3. 分项改进方案

### 3.1 M0：把 AI 辅助基线升级为生产级质量证据

当前基线报告和 10 条冲突裁决已经完成，且明确记录为 AI 辅助验收；这满足项目内部 M0 完成条件，但不满足“至少两名独立人类评审”的生产级质量声明。M0 的负样本明确拒答率为 0%，原因、证据、步骤评分也偏低，说明后续 M5 的改造必须以这组负样本和裁决准则为回归入口。

改进步骤：

1. 从 50 条固定评测集抽取至少 10 条原评审样本，并再抽取一组覆盖正、负样本的盲评样本；评审者不能看到实现版本和其他人的结果。
2. 使用已有 `double_review_annotations.csv` 字段，补充第二名非实现者的人类原因、证据支持、步骤可执行性和危险建议评分。
3. 对分歧样本执行预先定义的裁决规则，保存原始评分、分歧项、裁决理由和最终标签；不得用平均分掩盖冲突。
4. 将人类裁决结果固定为 M5 的 Gold Set，后续 Prompt、检索和模型变更均回归该集合。

完成条件：评审覆盖率达到计划要求，存在两名独立评审和可追溯裁决文件；基线报告同时注明 AI 辅助结果与真人结果，避免两者混称。

### 3.2 M1：补齐关键 API 覆盖、CI 合并门禁和依赖风险

当前后端核心模块覆盖率为 88%，已经超过 80%；但关键 API 覆盖率为 95%，低于 100%。此外，GitHub Actions workflow 已存在，分支保护仍需仓库平台配置；前端运行时依赖审计结果为高危 7、中危 2，也未达到风险表中的 0 项目标。

改进步骤：

1. 按 `deepseek_api/api.py` 的 19 个未覆盖语句建立分支清单，优先补充模型超时/不可用、重复提交、越权、空证据、限流、外部 URL 校验和异常映射测试。
2. 在测试中继续使用 Fake Provider、临时数据库和 Mock 网络；覆盖率提升不能通过降低排除范围或忽略规则实现。
3. 在 GitHub 仓库设置 required status checks，至少要求后端测试、前端测试、前端构建、lint/format 和 pre-commit 通过后才能合并；用一个故意失败的分支保护检查验证配置生效。
4. 对 `npm audit --omit=dev` 的直接依赖和传递依赖逐项确定升级路径。每次升级只解决一组相关漏洞，并运行前端测试、构建和主要登录/聊天流程；无法立即升级的漏洞要登记受影响路径和临时缓解措施。

完成条件：关键 API 行/分支覆盖率按计划口径达到 100%，CI 必需检查在平台侧实际阻止失败合并，高危/中危运行时漏洞降为 0 或由明确的风险接受记录替代。

### 3.3 M2/M3：把单实例正确性扩展为生产并发证据

M2 的模型隔离、Session/History、缓存和错误语义已经有单元测试与 PostgreSQL 单实例 50 请求/20 worker 证据；M3 的限流也已接入数据库共享 bucket。但现有证据明确不覆盖多进程部署、共享缓存后端和 MySQL，因此不能宣称跨部署形态达到 100% 一致性。SQLite 测试也不能替代真实数据库锁竞争。

建议建立统一并发矩阵：

| 维度     | 最低场景                                                | 必须观察的指标                                         |
| -------- | ------------------------------------------------------- | ------------------------------------------------------ |
| 数据库   | PostgreSQL、MySQL；每种执行迁移、回滚和清理             | 迁移成功、锁等待、死锁、重复写入、孤立 History         |
| 进程模型 | 单 worker、多 worker/多进程                             | 模型串台、Session/History 数量、错误率、P95            |
| 缓存     | LocMem 基线、Redis 等共享后端                           | 跨 worker 命中一致、跨用户污染、命名空间失效、击穿次数 |
| 限流     | 用户维度、IP 维度、登录/聊天/模型验证                   | 超额拦截率、误拦截率、429、Retry-After、bucket 竞争    |
| 写入压力 | 同一 Session 并发、不同 Session 并发、重复 `message_id` | sequence 唯一性、幂等结果、事务回滚、锁等待            |

执行要求：

1. 每个数据库和部署组合至少重复 3 次，固定请求集、worker 数、模型 Fake Provider 和数据清理方式。
2. 记录跨用户模型选择、History/Session 行数、缓存 key 命中结果和限流 bucket 计数；日志中只保留脱敏 ID。
3. 增加可在 CI 中运行的低成本并发回归，完整矩阵作为独立集成/夜间任务；失败时保留数据库、进程和请求摘要。
4. 若 Redis 尚未纳入当前部署，至少先完成多进程数据库语义验证，并把 LocMemCache 的生产限制写入部署检查，不将单进程测试结果外推。

完成条件：所有矩阵组合中模型串台、越权、缓存污染、重复写入和错误计数均为 0；限流超额拦截率 100%；迁移和回滚均有 PostgreSQL/MySQL 证据。高吞吐限流若继续使用数据库固定窗口，应另外报告其 P95、吞吐和锁竞争，并决定是否由 Gateway/Redis 令牌桶承担前置拦截。

### 3.4 M4：恢复并超过 legacy 检索质量

当前同一 1708 行公平子集上的结果为：结构化向量 Recall@5=0.90、Recall@10=0.90、MRR@10=0.8458；legacy 对应为 0.95、0.95、0.8646。虽然绝对目标中的 Recall@5、Recall@10 和 MRR 阈值满足，但 Recall@5 还要求“不低于基线”，因此当前 M4 质量尚未完全达标。Hybrid Recall@1 提升到 0.825，但 Recall@10 仍为 0.90；Reranker Recall@10 为 0.875，暂不应切换为默认策略。

建议按以下顺序做可归因实验：

1. 固定数据子集、查询集、Embedding 模型和版本，先建立 legacy、结构化向量、Hybrid、Reranker 四组可重复基线。
2. 对结构化模板做字段消融：原始行、完整模板、错误摘要优先、异常类型/组件/时间字段加权；保留 `document_id` 和来源 metadata，不以丢失可解释性换取分数。
3. 对 Hybrid 的候选倍数、向量/词法权重、阈值和 Top-K 做网格实验；每次只改变一个因素，并同时观察 Recall@5/10、MRR、负样本无证据率和延迟。
4. 建立独立 BM25 倒排索引，避免当前“候选集词法实验”与完整语料能力混淆；仅当独立索引在固定集上不降低质量且延迟可接受时，才考虑扩大默认候选来源。
5. 对 Reranker 记录模型、候选数、CPU/GPU、耗时和显存；以 Recall/MRR、引用支持率和生成总延迟共同决定是否采用，不以单一 Recall@1 提升作为上线依据。

完成条件：至少一套默认策略在同一评测口径下 Recall@5 不低于 0.95、Recall@10 不低于 0.95、MRR@10 不低于 0.8646，同时负样本无证据率不低于 90%。如果硬件约束下无法达到 legacy，应记录正式指标调整、原因、代价和产品接受人，不能只修改结果表。

### 3.5 M4：完成全量索引和真实切换/回滚演练

当前数据清洗得到 73912 条规范记录和 246951 个文档块，已完成全量版本化向量化和切换，当前版本为 `idx-69c72b8c2a56c2fea290`。固定集全量检索结果与 1708 行公平子集分开记录；全量 Recall@10=0.10，仍需处理跨源干扰。构建资源指标和多轮故障回滚演练尚未完成。

改进步骤：

1. 在 Ollama 空闲且配置固定的窗口执行全量分批构建，使用流式文档输入和受控 batch，避免将全部 Embedding 结果同时驻留内存。
2. 构建前生成 manifest，构建后核对输入记录数、文档块数、稳定 ID、metadata 覆盖率、向量维度、数据/Embedding/解析/分块版本和最终 collection 名称。
3. 在临时版本上注入中途失败、Embedding 超时和磁盘不足等故障，验证 current pointer 不变、旧索引可继续服务、失败版本可清理。
4. 通过状态命令记录构建开始/结束、批次、失败重试、切换时间和回滚结果；将资源指标写入 JSON 证据，而不是只保留终端摘要。

完成条件：全量 manifest 与 collection 计数一致，在线指针只在验收通过后切换，故障演练中在线索引不可用次数为 0；完整数据上的检索质量和资源数据单独报告，不与 1708 行子集混合。当前计数、指针和质量分开报告已完成，资源和故障演练仍待补齐。

### 3.6 M4：降低索引峰值内存并建立可比性能结论

当前索引峰值内存为 177876 KiB，目标是较基线下降至少 30%，因此该指标尚未达标。构建耗时 47.69 秒相对 50.77 秒的改善只有一次复测，且已经注明不能归因；冷启动也未完整测量。

改进步骤：

1. 先在 Ollama 空闲、相同进程参数、相同数据和 batch 下重复 legacy/当前实现各 3 次，报告中位数、范围和峰值 RSS；不要把资源竞争下的 203.4 秒结果作为优化结论。
2. 分离文档解析、Embedding 请求、Chroma 写入和临时列表的内存统计，确认峰值发生阶段。
3. 将管线改为有界生产者/消费者或小批次提交，及时释放已写入批次；避免保存全量 `Document`、向量和重复文本副本。
4. 分别测量 CPU、Ollama 和 Chroma 的资源，不把外部服务内存误算为 Django 进程内存，也不通过降低数据覆盖率获得表面下降。
5. 对构建失败、重试和吞吐设置上限；优化后必须重新跑 M4/M5 固定集，确认质量没有回归。

完成条件：在相同完整数据覆盖率下峰值内存较基线下降至少 30%；构建耗时至少有 3 次独立重复，给出中位数和离散范围；冷启动、索引复用、普通 API 和缓存命中分别测量。

### 3.7 M5：完成真实模型人工质量评审和发布门槛

DeepSeek 50 条固定集已经完成，自动化结果为 Schema 首轮/修复后 100%、有效引用 97.5%、无证据拒答/追问 100%、原因概念匹配代理 100%、步骤匹配代理 97.5%。其中原因和步骤是归一化短语匹配代理，不等同于“原因正确”和“步骤可执行”；引用有效也不等同于引用内容实际支持结论。计划要求的原因人工评分、步骤可执行性评分、引用实际支持率、总体质量提升和版本回归比例仍未闭环。

改进步骤：

1. 对 40 条正样本和 10 条负样本执行非实现者盲评；评审表至少包含原因正确性、每条引用是否支持结论、步骤可执行性、风险/不可接受建议、无证据时是否应拒答。
2. 至少两名评审者独立评分，原因和步骤使用 1～5 分量表；引用按支持/部分支持/不支持计数，并保留证据 ID 和评语。
3. 对评分差异超过预设阈值的样本进行裁决，报告平均分、达标比例、分歧率和裁决后结果；不能把自动代理率直接填入人工评分栏。
4. 用同一固定模型参数、数据版本、索引版本和 Prompt 版本运行当前版本与基线版本，计算总体质量提升和单样本回归比例。
5. 对 8 条 Prompt Injection 样本补做真实模型复核，检查模型是否泄露系统指令、改变任务目标、绕过证据门禁或给出危险操作；夹具通过不能替代真实 Provider 验证。

完成条件：引用实际支持率 ≥90%，原因人工评分 ≥4.0/5，步骤可执行性 ≥4.0/5，无高危 Injection 成功样本，总体质量提升 ≥10%，单次版本回归 ≤5%；报告由至少一名非实现者复核并登记为新的验收证据。

## 4. 推荐执行顺序

### 阶段 A：先补证据，冻结比较口径

1. 冻结当前配置、数据 manifest、模型/Embedding、Prompt 和评测集版本。
2. 完成 M5 盲评与裁决，形成 Gold Set。
3. 在空闲 Ollama 条件下完成 M4 子集三次重复，并保留当前 legacy 对照。

### 阶段 B：修复实际低于目标的指标

1. 用 M4 参数/模板消融找回 Recall@5/10 和 MRR 的 legacy 差距。
2. 全量索引已构建并发布；补充失败回滚、多次重复和资源测量证据。
3. 按阶段拆分内存峰值，实施有界批处理后复测质量与性能。

### 阶段 C：扩大部署与工程验收范围

1. 完成 PostgreSQL/MySQL、多 worker、共享缓存和限流并发矩阵。
2. 补齐关键 API 未覆盖分支，配置 CI required checks 和分支保护。
3. 处理运行时依赖漏洞，并完成前端主流程回归。
4. 用新的证据更新 `development_plan.md` 第 17、18、19 章，再决定是否可以勾选 M1～M5 的最终 Checklist。

## 5. 验收证据清单模板

后续每个缺口关闭时，至少新增以下信息：

| 信息       | 要求                                                                      |
| ---------- | ------------------------------------------------------------------------- |
| 版本身份   | Git commit、配置哈希、数据 manifest、索引版本、Embedding/LLM、Prompt 版本 |
| 运行条件   | CPU/GPU、内存、worker、batch、数据库、缓存、网络和并发数                  |
| 指标结果   | 原始分子/分母、均值/中位数/范围，不能只写百分比                           |
| 失败语义   | 超时、模型不可用、无证据、锁冲突、回滚和限流分别统计                      |
| 质量复核   | 原始评分、评审者角色、分歧、裁决和非实现者确认                            |
| 可复现入口 | 命令、固定输入路径和输出证据路径；真实模型评测与普通回归分离              |

只有当指标、范围和证据都满足计划要求时，才将总计划中的 `[ ]` 改为 `[x]`。若因硬件或部署约束调整目标，必须先增加 ADR，说明原目标、实测证据、调整理由、影响和接受人。

## 6. 当前不纳入本次整改清单的项目

- M6 的流式、共享缓存击穿治理和性能指标；
- M7 的 Trace、Readiness、故障演练和部署自动化；
- M8/M9 的 Agent Workflow、只读工具和 Multi-Agent 对照实验；
- 仅有“未开始”状态且尚无实现证据的其他指标。

这些项目不是本轮“已完成改造但未完全达标”范围，应在对应里程碑开始后单独建立基线和验收证据。
